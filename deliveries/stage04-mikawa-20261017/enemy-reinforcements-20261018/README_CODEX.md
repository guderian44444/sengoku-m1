交給接手第四關的 Codex／工程夥伴。請把本包的出兵配置與排程接入目標專案，保留現有第四關素材、招式和地形規則。這份交接本身沒有修改 runtime 或 Git，也沒有完成遊戲實測。

## 先讀與實作範圍

舊稿多數進軍只有 1–3 名敵兵，且無增援，導致入場太空。新版沿第三關人口管理的做法，將「初始敵人」「有限增援批次」「同場上限」分開。

優先順序：
1. 使用者最新要求：每一小段另補 2–3 波，每波由兩方向進，共 6–8 人，每邊 3–4 人；初始另計，王關也適用。
2. 本包 stage04_density_v2.json 的 13 節點數量與左右編成；不要重排、加倍率或擅自省略王關波次。README 的排程細節是 JSON 的實作澄清，不更改數量。
3. 既有第四關已核招式、吉良六弓、泥地、盾牌、橋頭無 NPC 等規則；僅舊表「無增援／僅初始敵清場」被本次新要求取代。
4. 第三關程式只是出兵管理參考，不要直接覆蓋第三關，也不要把第三關無限補兵／突破條件整套搬過來。

文件入口：
- stage04_density_v2.json：原樣保留的配置資料，非引擎原生 config；透過 adapter 接線。
- stage04_density_v2.md：每節初始與各波左右組成。
- enemy_id_mapping.json：已查的設計 ID／素材 key，runtime 對應待核。
- TEST_MATRIX.md：必測案例及預期結果。
- stage03_reference_report.md、source_file_hashes.json：第三關實碼依據、查閱日期及 blob SHA。

## 人口統計與同場上限

- `regular_alive`：目前節點活著的普通兵，包含正在從場外進場的兵。富永、吉良、長照不在此池；吉良護衛另池。
- `escort_alive`：僅吉良節點中掛上 escort_pool 標記的活弓兵，含進場中。
- `boss_alive`：活著的本節王。敗退後倒地／起身／逃離演出不是活戰鬥人口。
- `reserved_regular`、`reserved_escort`：已預約尚未建立角色的名額，兩者不得互用。
- `occupied = regular_alive + escort_alive + boss_alive + reserved_regular + reserved_escort`。
- 同場 cap：普通節點 10；富永／長照 11（含王）；吉良 15（王 1＋護衛 6＋普通最多 8）。玩家、屍體、旗、拒馬、柵欄及背景助陣 8 人不計活敵，也不能計為待清敵。
- 普通池 cap：一般節點及富永／長照 10；吉良 8。吉良 escort_alive＋reserved_escort ≤ 6。
- 系統若另有 actors 陣列 48 上限，屍體可能仍占該技術容量。它只暫緩建角，不修改本節敵軍總數，也不表示玩家必須殺 48 人。

預約整批時，在同一個 simulation tick 內檢查並原子增加名額。每建一名，原子消耗該名 token 並加入 alive；不要同時把同一名算成 alive 和 reserved。左右兩名應整對預檢並一併提交；任一側找不到合法入口時保留該對 token，延後重試，避免單側偷偷吃滿 cap。重試不能新增 token。候補名額、活敵、入場中必須從同一份權威 state 統計，不用畫面可見數取代。

## 有限波排程與精確時間

採 60 Hz simulation ticks。這次預警與入場間隔都為 45 ticks＝0.75 秒，不是泛用普通波的 75 ticks，也不是第三關死亡補兵的 240 ticks。

1. 初始化本節一次，建立獨立 initial roster、有限批次清單、boss／escort pool。普通初始兵可見地站在前方戰區；不要把它們藏在蘆葦。王介紹期間停攻擊和入場計時。
2. 開下一波的條件：前一波（第一波則初始）已全數完成入場、沒有該批 pending token，且 regular_alive ≤ 2。王和吉良六弓不列入這個「≤2」判斷。不要等所有敵死光才開。
3. 同一 tick 預約整波所有名額，固定波號，不再重新評估／重複發波。立即給左右場外來兵預警；預警不得新增落點提示或改吉良箭雨 UI。
4. 預約時刻 T，第一對最早 T+45；其後 T+90、T+135，8人波再 T+180。每對左一、右一；隊列按 JSON 左右種類的確定順序展開。若因碰撞／cap／技術容量延後，下一對不得早於上一對實際成功建立後 45 ticks，不追趕一次爆量。
5. 角色從鏡頭左右外進，行走進場，不能在玩家旁或畫面中瞬移；找可走平地與合法深度 lane，不生在未破柵欄、玩家或角色身上。世界邊界太靠近鏡頭時，必須核目標引擎合法 offscreen approach／遮蔽方式，不能改成只有單方向。
6. 本波所有角色都完成進場、所有預約已消耗後，才能評估下一波；不在第3對「建立但仍遠在場外」時立刻開另一批。
7. 每節 2–3 波全部發完後進 draining。要求 initial 與有限波清完、pending／reserved 全空，再依個別王條件完成。不得由畫面暫時沒有敵人宣告清場。

此規則最大重疊普通活兵為殘存 2＋新波 8＝10；吉良新波固定 6，因此普通池最多 2＋6＝8。313 是全關固定排程最低總人數，不是同場人口；吉良替補另計。大量波次的總時長、雙方向公平性及畫面可讀性仍須實測，不因未測自行刪波。

## 吉良的兩條隊列

node10 初始是吉良 1＋固定護衛弓兵 6，普通初始 0。王介紹完成且護衛初始入場完畢，有限近戰第一波即可開始預警。三批近戰各 6 人獨立於六弓。

護衛死一補一，原設計 180 ticks＝3秒延遲仍保留為可調初值，最短 admission 間隔 45 ticks。每次經確認且尚未處理的護衛死亡只預約一個 token；同一死亡事件不能重複補。上限含已預約始終 6，護衛總替補次數在吉良活著時不設有限總數。普通近戰死亡不觸發護衛補兵。

吉良 combat_defeated 必須先於同 tick 的護衛 spawn 處理：標記 boss 不再 active，取消護衛所有未落地 token／timer／reservation。已經存在且活著的護衛繼續戰鬥且須清掉。有限近戰三波及其預約不可被此取消。不能共用一個 cancel_all_spawns() 把有限波也刪掉。

命令箭雨只 snapshot 既存存活護衛，每波再檢查能否射擊；新補員不加入本次命令。保持原地四波、出手前追蹤／出手鎖定、範圍兩軸×1.5、無落點提示；不新增或集合弓兵，不把三批近戰加入箭雨名單。

完成條件：吉良敗退 AND 六弓補兵已取消且 reservation=0 AND 活護衛=0 AND 三批有限兵全部入場並擊敗 AND 普通 pending/reserved=0。

## 富永與長照的早死和通關

富永 node8：原招式和向前貼地劍氣全留；初始王＋4兵，另兩波各6。若玩家先擊敗富永，兩波與已在場普通兵照樣要解決；不能用 boss_dead 直接開出口。

長照 node13：原重甲、滿蓄力只站立暈眩、大迴旋、震地／三連震、隨身三連高速投石等全部保留。初始王＋4兵，另6／8／8三波，背景8名只演出。

王死亡不鎖血、不給無敵、不等普通兵全死才讓王死。按既有順序即刻演倒地→起身→逃離；逃到既定終點時只設定 `escape_complete=true`。原本直接發 stage_complete 的回呼要換成共同完成判斷，並以 `completion_emitted` 去重。

`can_complete = udono_combat_defeated AND escape_complete AND finite_batches_exhausted AND regular_alive==0 AND reserved_regular==0 AND pending_admissions==0`。

若兵先清完，等逃離；若王先逃完，等剩餘有限兵。兩條路都只發一次完成，不回生王，不因最後一兵／逃離回呼同 tick 重複發事件。

## 重試 存檔與多人

- 一次節點生命週期用 encounter_epoch，波號 batch_index，左右入場 token 使用固定 ordinal／唯一 ID。死亡事件、初始生成、波預約、建角、終戰完成都需冪等。
- 同節點重訪、frame callback重試不重新初始化；只有明確死亡重試／重開才建立新 epoch 並從乾淨初始計畫開始。舊 timer、token、事件回呼因 epoch 不符必須失效。
- 若目標已支援節點中途存檔：一起保存 epoch、已發／待發波號、每側ordinal、剩餘時間、token狀態、活角色ID與pool、護衛死亡去重、boss／escape／completion狀態。恢復後重建既有排程，不呼叫新一輪 begin。若現有產品只支持checkpoint重啟，沿用它並明說，不為本任務新增整套中途存檔。
- 1人／2人均使用本包同樣初始、批次、左右人數及cap；不要再套 _scaled_wave 的雙人+50%，否則6–8人要求被破壞。不要把本包又乘1.5後外層再乘一次。
- 既有第四關HP／傷害／難度／多人HP策略維持，不在本交接重新改數值。若目標實作缺這些映射，要回報，不把第三關1.35自行當第四關王設定。
